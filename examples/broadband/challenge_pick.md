# Picking the challenge track

Applies the strategy in `README.md`: maximise the chance of **winning a track**. Weights: competition (1) and difficulty (2) count double; fit to my profile (3) counts once. Prize size is ignored.

Copy this file into the event's folder and fill it in there.

## From the event brief

Event brief: 
Tracks published: 5
Choice made: before the company briefings
Places limited (first come, first served): yes

After the deadline, building time matters more than a better pick. If places are limited, select as soon as you can: waiting risks the first choice filling up.

## Before the event

- [x ] Read every track as soon as it's published (platform, Discord, e-mail). Pre-score them below.
- [ x] Rank at least 3, so a full track doesn't force a rushed choice.
- [ ] For each shortlisted track, write 2-3 questions for its mentors (data access, what a winning demo looks like, how they judge).
- [x ] Check each shortlisted track's IP terms (public repo allowed or not).
- [x ] Note which tracks need hardware, and how it's handed out.

## On site (only if the choice comes after the briefings)

Gather evidence, don't guess:
- **Competition:** how many people at each partner's booth after the opening, how active each track's Discord channel is, and *who* they are (experienced teams, robotics clubs, partner-domain experts).
- **Difficulty:** is the data available tonight? Is there a clear "done" in the build time? Does it need hardware I don't have?
- **Judging:** ask how winners are picked (demo at booth, slot time, criteria). Write it into `CLAUDE.md` §1.

If the choice comes first, score from the published summaries and save these questions for the briefing.
